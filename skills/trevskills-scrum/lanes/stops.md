# Stops

Every `B ask` reads as Issue / Options / Recommended. The question is the Issue; never write the words Issue or Options into it.

- **Issue:** the machine prefix, first and unchanged (`Hard stop: schema — `, `blocked: `, `debug: `, ...), then plain words that say what happened and why it needs Trevor; the options plus the `--recommend` `<why>` say what each button does. The dashboard hides the prefix, so the text after it must read on its own. The question and the `<why>` never use a file path, a file pointer (`see ci.md`), a rule number or an internal term (`human-only`, `lane`, `hard stop`, `rework`, `BigBoy`) without saying what it means. Name `stop.md`, `ci.md`, `check.md` or `decision.md` by bare name only. Example: `This change adds a database column, which agents aren't allowed to apply on their own. Reviews and tests passed. Apply it and merge?` Every number in a question names what it measures and its limit: `1-minute CPU load average 14 on an 8-core Mac (limit 8)`, never load above 8.
- **Rewrite:** whoever composes the ask rewrites any templated or passed-through text (a lane template, decision.md line 2, an unblocker `## For Trevor` line) to meet this bar before calling `B ask`, keeping its prefix.
- **Detail:** file lists, logs and anything long go in `jobs/<id>/stop.md` (`$F/jobs/$ID/stop.md`), written before the ask; the question says in words what the detail holds and where it is shown (e.g. `the full file list is in the stop.md tab of this job`).
- **Options:** the A/B/C trio where it fits: A carry on or merge (`Carry on`, `Try again`, `Merge anyway`), B send back with a note (`Send back with a note`), C remove this job (`Remove this job=abort <id> --cascade`). A `--requeue` option reads `Put back on the backlog`. Labels are plain words, never a bare `Abort`.
- **Title:** `--title <KEY>` right before `--recommend`, one key from this list, exact and in capitals. The dashboard shows it, with `_` as a space, as the heading of the stop. `board.py ask` refuses any other value. The keys: `UNCOMMITTED_CHANGES`: the main checkout or the job's worktree has files nobody committed; `WRONG_BRANCH`: the main checkout is on another branch, or the profile's Base branch line is malformed or missing on origin; `MERGE_CONFLICT`: the branch still conflicts with the default branch after two tries; `CHECKS_FAILING`: tests or CI still fail after the allowed fix attempts (debug fixes included); `MERGE_BLOCKED`: GitHub will not take the merge (the PR was closed, the merge or done step was refused, or the GitHub CLI is missing or signed out); `DATABASE_CHANGE`: the job changes the database structure, and the migrate needs an OK or it stopped; `ROUND_LIMIT`: the approver asked for a second round of fixes, and a job only gets one; `BUILDER_BLOCKED`: the builder, debugger or approver could not go on (`blocked:`, `debug: blocked`, `Hard stop: blocked`); `REVIEW_ESCALATED`: the approver escalated for another reason (`Hard stop: render`, any other decision line, or output that could not be read); `BIGBOY_OFF_TRACK`: the tracker says the remaining tickets no longer reach the goal; `BIGBOY_BLOCKED`: a multi-ticket job cannot start its next ticket, because the chain lock is held or its children are blocked; `DEPENDENCY`: a job this one waited on finished, was aborted or was removed; `MD_CONTRADICTION`: a knowledge-save job found a fact that contradicts the target .md or the code; `DIGEST`: a weekly digest proposal, a digest edit that failed to apply, or a pipeline-health finding.
- **Recommended:** `--recommend <key> '<why>'` after the last option. `<key>` is the option you advise, picked by your own judgement; `<why>` is one short reason with every `'` removed. It is its own reason, never a `<why>` the question or an option already uses.
- Machine load (CPU load average, RAM, swap) is never a reason to `B ask`: a heavy run waits in a lock, or runs anyway.
- A re-ask passes the same question, options, `--title` and --recommend, because an ask without `--recommend` drops the advice and an ask without `--title` is refused.
